How the Roxi agents work

Eleven components, four of which are agents in the daily run and four of which contain no model at all. This describes what the code in roxi/ actually does, not what the plan says it should.

What counts as an agent

Three different things get called “agents” in conversation. In the codebase they are strictly separated, and the separation is the point: anything that must be predictable contains no model.

Worth noticing: only the four daily-run agents read their model from the vertical config. Compiler, Responder, Planner, Director and Reviewer import module constants directly, so switching models for those means editing Python rather than YAML. Fine for now, inconsistent later.

Anatomy of one agent call

Every model call in the system goes through a single function, structured() in llm.py. No agent talks to the Anthropic client directly except the Researcher and Compiler, which need web search. The path:

  1. A Pydantic class defines the output. schema.model_json_schema() becomes a tool definition — the class is the contract.
  2. The call forces that tool. tool_choice={"type":"tool","name":schema.__name__} means the model cannot reply with prose. It must emit the structure.
  3. The response is searched for a tool_use block, and its .input is validated back into the Pydantic class.
  4. On validation failure, one retry. The failed tool_use is appended to the thread along with a tool_result carrying the actual error text, so the model sees precisely what was wrong. It uses the real block id — an invented id would break the thread.
  5. Second failure raises ExtractionError. Agents catch it and return None; the pipeline logs and moves on. One bad item never kills a run.
  6. Every attempt writes a trace row — model, agent, tokens, cost, latency, outcome, plus a prompt_version (SHA of the system prompt) and input_hash. Successes and failures alike.

Why prompt_version matters: it is a hash of the system prompt, so it changes automatically when a prompt is edited. Months later it is what separates “quality dropped because I changed the prompt” from “quality dropped because a source changed its markup.”

Pipeline one — setup, runs once

python -m roxi compile starts an interactive session. This is the only place a model holds a conversation.

AskTwo prompts at the terminal: what you sell, and your website URL.
SearchThe Compiler reads the site with web search and forms a view of the market.
InterviewA loop: the model asks, you answer, the thread grows. It is told to press hardest on disqualifiers.
EmitWhen ready it calls EmitVerticalConfig, and the YAML is printed for review with the session cost.
DecideAccept, edit, or quit. Rejection feeds your words back as a tool_result and the loop continues.

The instruction that does the most work: “Disqualifiers must be unambiguous. ‘Too small’ is not a disqualifier. ‘Fewer than 8 trucks’ is.” Every rule has to be checkable against one signal field, because the Scorer downstream can only apply rules of that shape.

Pipeline two — the daily GTM run

pipeline.run() is about eighty lines of sequential Python. Nothing re-plans; a human can read the whole run top to bottom.

CollectJob boards, registry, Reddit. Each wrapped in try/except — a broken collector logs an event and the run continues with whatever the others returned.
ExtractHaiku, every item. Drops anything where no company can be named.
DedupePure code. Exact signal hash, then fuzzy company match against 30 days of history.
ScoreHaiku, every survivor. Disqualifiers checked first; additive deltas otherwise.
The gate — score >= qualify_threshold, then [:daily_research_budget]

Two cuts, both in config. Above this line runs on Haiku across hundreds of items; below it runs on Sonnet with web search across roughly fifteen. That is where the cost is, and why the gate is a number rather than a judgment call.

ResearchTwo calls: a search turn that browses, then a clean extraction turn that sees only the notes. No results, no lead.
DraftSonnet. Refuses to run at all without a research brief.
Store & deliverA row per lead, then a Slack card. Run totals and cost written back to the runs table.

How each daily agent is instructed

AgentThe rule that shapes its behaviour
Extractorevidence must be copied word for word. Never paraphrase. Fleet size only when stated — not inferred from tone or industry cues.
ScorerDisqualifiers first, then additive deltas, each recorded in rules_fired so the sum can be checked. Explicitly forbidden from writing sales-facing prose.
ResearcherOnly record what search verified. Thin results mean confidence: low and fewer hooks, never padding. Titles only, never invented names.
DrafterUnder 120 words, open on the researched fact, one small ask. Banned words are named individually. Low confidence means a shorter email, not a longer one.

Pipeline three — replies and sending

Responder model

One agent for every channel, because “not interested” means the same thing by email or text. Seven intents: interested, not now, wrong person, out of office, unsubscribe, hostile, other.

The prompt tells it to be deliberately trigger-happy about unsubscribes — a false positive costs one lead, a miss is a compliance breach. Unsubscribe and hostile write to the suppression list immediately, before any human sees the reply.

Dispatcher code

No model. It sends only leads whose status is approved, checks the suppression list before each send, and writes an audit row either way. It has no discretion by design — the one step that must be predictable is the one that touches the outside world.

Known defect — do not send from this yet

The current adapter constructs the recipient address as contact@{domain}. That is a guess: it bounces, damages sending-domain reputation, and undercuts any implied-consent position under CASL. See 09-known-bugs.md H1 and M5 before Phase 3.

Pipeline four — content

Planner3–7 items a week, each with a specific angle. Told that “post about our product” is not a topic. Never proposes Reddit or LinkedIn.
DirectorWrites the production brief: finished copy for text, a detailed prompt for image, a script and shot list under 90 seconds for video.
GeneratorsAdapters, no model. Costs recorded per asset in generation_costs.
ReviewerThe skeptic. Checks brand voice, claim substantiation, platform fit, and screenshot risk.
PublisherCode. Rate-limited per platform, audit row per attempt, refuses unapproved assets.

Two details in the Reviewer worth keeping. It is told to find problems rather than approve things — the opposite disposition to the Director, which is why they are separate calls. And it is explicitly told not to invent problems to seem thorough, because a reviewer that always finds something teaches people to ignore it.

The Publisher enforces its limits in code, not prose. _FORBIDDEN_PLATFORMS is a frozenset containing reddit and linkedin, and passing either raises ValueError before anything else runs. A rule written only in a system prompt is a suggestion; this one cannot be talked around.

What holds it together

Typed handoffs

RawItem → Signal → ScoredSignal → ResearchBrief → EmailDraft. Each stage receives a validated object, never a transcript. The Scorer sees seven clean fields serialised as JSON — never the eight thousand characters of scraped HTML the Extractor read.

Failure is local

Agents return None rather than raising. A failed extraction drops one item; a failed collector drops one channel; a failed research call drops one lead. The run always finishes and always writes its totals.

Everything is traced

Five tables carry the record: runs for totals, llm_calls for every model call, events for pipeline milestones, publish_log and generation_costs for the content side. The run id threads through all of them, so any lead can be traced back to the exact calls that produced it.

The rules that live in code, not prompts

  • Dedupe — hashing and string similarity, no model involved
  • The threshold and research budget — two config numbers, applied by the pipeline
  • Suppression — checked by the Dispatcher before every send
  • Forbidden platforms — a frozenset that raises
  • Approval — the Dispatcher only ever reads status == "approved"

Anything that must not be negotiable is not phrased as an instruction to a model.

Current state

All eleven components exist. The eval harness has never been run, so no baseline exists for scoring quality, and fourteen defects are logged in 09-known-bugs.md — two of them blocking, including stale model IDs that make every Sonnet call fail. Read that document before running anything described here.
