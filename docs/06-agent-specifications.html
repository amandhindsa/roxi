Roxi agent specifications

Five narrow agents, orchestrated by plain code. Each does one job, sees only what that job needs, and hands off a validated object rather than a conversation. The set is fixed for every customer — what changes between them is the config one of these agents writes.

Roxi / docs / 06  ·  first vertical: Hauler AI, Canadian carriers

Setup — runs once

A customer describes their business in plain language. Nobody hand-writes a spec sheet per domain, and nobody edits YAML.

CompilerInterviews the user, then emits the vertical config the four run-time agents read.
ReviewUser confirms or edits the rules in plain English. Human present, ambiguity resolved once.

The run — daily

One pass, top to bottom. No agent decides what happens next — pipeline.py does, and a person can read it.

CollectorsJob boards, registry filings, forums. Raw text, zero interpretation.
ExtractorEvery item. Pulls typed facts out of the mess.
DedupePlain code. Exact signal key, then fuzzy company match with a 30-day cooldown.
ScorerEvery survivor. Applies the vertical's rules and returns a number.
Threshold gate — score ≥ 70, capped at 15 per day

Everything above this line runs on Haiku against hundreds of items. Everything below runs on Sonnet against a handful. Roughly twenty times the unit cost crosses here, which is why the gate is a hard number in config and not a judgment call.

ResearcherQualified only. Searches the web, verifies, builds a brief.
DrafterWrites the opener and the line explaining why today.
DeliverySlack card. A person approves. Roxi never sends.

Compiler

Compiler

claude-sonnet-5 + web search

Turns “we sell dispatch software to Canadian carriers” into a working vertical. It runs at setup, with a person in the room, and everything it produces is reviewable in plain language. This is the only agent whose output a human edits.

SeesThe user's description of their product and buyer, their website, and answers to its own clarifying questions
EmitsVerticalConfig — product brief, ICP description, scoring rules with numeric deltas, disqualifiers, threshold, channel selection
ToolsWeb search, to read the customer's own site and category

Does

  • Ask what a bad customer looks like — disqualifiers are where most of the accuracy lives, and users rarely volunteer them
  • Propose scoring rules as stated deltas, not descriptions of taste
  • Select channels from the available tiers and say plainly which are unavailable for this domain
  • Warn when a domain has no publicly observable buying signal, rather than shipping a bad first run

Does not

  • Run at execution time — it compiles once, then the config is frozen and versioned
  • Invent a channel that no collector supports
  • Emit anything the user cannot read and change

Failure mode: agreeable vagueness — rules like “good fit for growing companies” that a Scorer cannot apply. Every rule it emits must be checkable against a single signal, or it is not a rule.

Scope note: Rilo's builder compiled arbitrary workflows, an unbounded output space that needed a hundred connectors and a self-correcting runtime to survive. This one emits config for a pipeline that already exists. Same natural-language onboarding, a fraction of the failure surface.

Extractor

Extractor

claude-haiku-4-5

Turns a scraped job posting, filing, or forum thread into structured facts. It reads literally and makes no judgment about whether the company is worth contacting.

SeesRawItem — channel, source URL, title, body (first 6,000 chars)
EmitsSignal — company, domain, location, fleet size, signal type, date, evidence, poster role, identifiable flag
ToolsNone

Does

  • Names the company and pulls fleet size only when stated or clearly implied
  • Captures a verbatim sentence as evidence, never a paraphrase
  • Classifies the poster from how they write — “my dispatcher” is a driver, “my drivers” is an owner
  • Flags items where no specific company can be named

Does not

  • Guess a fleet size from tone or company size cues
  • Decide whether this is a good lead
  • Clean up or improve the source wording

Failure mode: inventing a fleet size that reads plausibly. The verbatim evidence field is the check — if the number is not in the quoted sentence, it was invented.

Scorer

Scorer

claude-haiku-4-5

Applies the vertical's stated rules to one clean signal and returns a number with its arithmetic shown. It is the skeptic in the pipeline and it writes nothing a prospect will ever read.

SeesA Signal and the ICP rule list. Never the raw source text.
EmitsScoredSignal — score 0–100, rules_fired with deltas, internal reasoning, disqualifier
ToolsNone

Does

  • Apply rules literally and additively from a stated baseline
  • List every rule fired with its numeric delta, so the sum can be checked
  • Return zero and name the rule when a disqualifier fires

Does not

  • Write why_now or any sales-facing sentence
  • Consider whether the lead could be made to sound appealing
  • Award points for something the evidence does not support

Failure mode: optimism. An earlier version had the Scorer write why_now alongside the number, and once a model has composed a persuasive line it has committed to the lead being good. Scoring and copywriting were split for exactly this reason.

Researcher

Researcher

claude-sonnet-5 + web search

Takes a qualified carrier and finds what a salesperson would want to know before the first call. Runs as two calls: one that searches, then a clean one that sees only the notes.

SeesCompany name, location, the signal, and the product brief
EmitsResearchBrief — summary, fleet estimate, lanes, current stack guess, decision-maker title, hooks, confidence
ToolsWeb search only — the single tool it needs, and nothing else

Does

  • Look for the company site, fleet size, lanes, cross-border activity, and any named software
  • Include only facts it could verify in the hooks
  • Return confidence: low and fewer hooks when searches come back thin

Does not

  • Invent a contact name — decision_maker_title is a title, not a person
  • Pad a thin brief to look thorough
  • Pass raw search results downstream

Failure mode: confident fabrication when a small carrier has almost no web presence. The confidence field exists so the Drafter can write a shorter email instead of dressing up a guess.

Drafter

Drafter

claude-sonnet-5

Writes the first-touch email and the one-line reason this carrier is worth contacting today. It is the only agent allowed to be persuasive, and it writes to people who delete marketing email on sight.

SeesSignal, score with rules fired, research brief, product brief
EmitsEmailDraft — why now, subject, body, hook used
ToolsNone

Does

  • Open with the specific researched fact, not with who we are
  • Stay under 120 words with one concrete product claim
  • Make one small ask — a reply, not a demo
  • Name which hook it used, so bad openers are traceable

Does not

  • Write greeting filler or words like “seamless”
  • Add a detail that is not in the brief
  • Send anything

Failure mode: smoothing over a thin brief with generic freight language. A short, specific email beats a long, plausible one, and the model needs telling.

The control plane

Every step writes a trace row before it writes anything else: run id, org id, agent, prompt version, input hash, output, tokens, latency, cost, and outcome. The interface can come later — the rows cannot be reconstructed after the fact.

Prompt version on every row is what answers the question that will eventually matter: did quality drop because of a prompt change, or because a source changed its markup?

  • What the customer seesTheir own runs, in full. Every lead with its evidence and the rules that fired, and every item dropped with the reason. They are approving mail sent under their name and their domain — asking anyone to take responsibility for reasoning they cannot inspect is a bad trade, and when a card is wrong it is the only way they can tell you why.
  • What the operator seesHealth across all tenants: step failure rates, collector yield, cost per org, prompt-version performance, eval results over time. A collector silently returning zero rows is the most common real outage and the least visible one.
  • What nobody seesLead data across tenant boundaries. Aggregate metrics in the admin console, never another tenant's prospects. If two customers ever compete, cross-tenant visibility is a breach waiting to happen — so the boundary goes in before the second customer, not after.
  • Controls, not just dashboardsPer-org spend caps enforced in the execution layer, a kill switch that halts a vertical mid-run, and an allowlist of what each org's agents may touch. Deny rules take precedence over allow rules, enforced centrally so no individual tool can bypass them.

There is a compliance edge here too. Roxi processes information about real people at real companies on a customer's behalf; under BC PIPA and equivalents they carry obligations they cannot discharge if they cannot see what was collected. Tenant-facing traces are part of how they meet them.

Why the boundaries sit where they do

  • One decision type per callIf two outputs would pull the model in opposite directions, they belong in different calls. Scoring wants skepticism; drafting wants warmth. Extraction and role classification both want literal reading, so they share a call.
  • Context isolation is the quality leverThe Scorer sees six clean fields, never 8,000 tokens of scraped HTML. Judgment degrades in proportion to junk in the window, and this is invisible while you are using a single agent because you never see the clean version.
  • Typed handoffs, not conversationSteps pass validated objects. The Drafter cannot be confused by the Extractor's reasoning because it never sees it.
  • One tool, or noneGive a model twelve tools and it picks wrong. The Researcher has web search and nothing else, so there is no wrong choice available.
  • Compile at setup, execute at run timeThe Compiler is the only agent that resolves ambiguity, and it does so once, with a person present. Everything downstream executes against a frozen, versioned config. This is what keeps daily runs reproducible and cheap.

The reliability arithmetic

This is the whole case for splitting the work up, and it is worth keeping visible:

one agent, five jobs   0.90⁵ = 59% end to end   — and no idea which part failed
five agents, retried   0.99⁵ = 95% end to end   — with a trace showing exactly where

Each step retries independently against its own schema. A validation failure gets one retry with the error fed back, then the record is dropped and logged rather than passed downstream half-formed.
